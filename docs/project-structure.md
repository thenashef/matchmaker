# Project Structure

A map of what lives where in this repository, and why. For *what's been built and what's next*, see `build-plan.md`. For the *why* behind specific design decisions, see the docs under `specs/` and `superpowers/`.

## Top level

```
matchmaker/
├── pom.xml                    Maven build file (Java 21, JUnit 5)
├── .gitignore                 target/, .superpowers/, IDE files
├── MatchMaker.v1 (1).docx     Original course-provided spec (Hebrew)
├── MatchMaker_Spec_EN.md      English translation of the spec
├── docker-compose.yml         Local MySQL: matchmaker (dev/demo) + matchmaker_test (the 5 DB-integration test classes)
├── db/                        SQL schema/seed scripts applied to the Dockerized MySQL
│                              (schema.sql auto-applies on first boot; seed-demo-users.sql is
│                               opt-in, run it yourself when you want demo player/admin accounts)
├── docs/                      All project documentation (see below)
├── src/main/java/...          Production code
├── src/main/resources/        db.properties (JDBC URL/credentials for DataSourceFactory)
└── src/test/java/...          Tests (mirrors the main tree, package-for-package)
```

Build/run commands, from the project root (requires `JAVA_HOME` pointed at a JDK 21):
```bash
mvn compile     # compile only
mvn test        # compile + run all tests
```
`ServerMain` is a real runnable entry point once compiled. A bare `java -cp target/classes ...` no longer works — this branch added runtime dependencies (HikariCP, mysql-connector-j, jbcrypt) that aren't on that classpath, and there's no shade/assembly plugin bundling them. Instead, run it through Maven, which already knows the full dependency classpath:
```bash
mvn exec:java
```
(`exec-maven-plugin` is configured in `pom.xml` with `com.matchmaker.server.ServerMain` as the default main class, so no `-Dexec.mainClass` is needed.) Starts an RMI registry on port 1099 and binds `AuthService`, `PlayerService`, `AdminService`.

## `src/main/java/com/matchmaker/` — production code

### `common/` — shared between server and every client
Nothing in `common` has any real behavior — it's the *contract* both the server and every client (player, admin) compile against. Neither client exists yet (steps 8–9), but the contract is written so they can be built independently once the server side is ready.

- **`common/dto/`** — plain, `Serializable` data-holder classes that cross the network via RMI (and later JMS). Each mirrors either a database table (per the spec) or a request/response shape:
  - `UserDTO` — a user's public profile (no password field — that never leaves the server).
  - `MoveDTO` — one row of move history.
  - `GameStateDTO` — the live snapshot of a game session (board state, whose turn, winner if finished).
  - `LoginResultDTO` — bundles a `UserDTO` with a session token; the one deliberate exception to "no request/response wrapper objects," because `login()` genuinely returns two distinct things.
  - `GameTypeDTO` — a game type's catalog entry (name, board dimensions, etc.).
  - `ChatMessageDTO` — one in-game chat message.
- **`common/enums/`** — `GameStatus` (`ACTIVE`/`FINISHED`/`ABANDONED`), `QueueStatus` (`WAITING`/`MATCHED`/`CANCELLED`).
- **`common/exceptions/`** — the checked-exception hierarchy every RMI call can throw. `MatchmakerException` is the base; `AuthenticationException`, `UsernameTakenException`, `NotParticipantException`, `NotYourTurnException`, `IllegalMoveException`, `NotAdminException` all extend it. Checked (not `RuntimeException`) so they fit naturally alongside RMI's own mandatory `RemoteException`.
- **`common/rmi/`** — the three RMI remote interfaces, split by *who calls them*, not by internal concern:
  - `AuthService` — `register`/`login`/`keepAlive`. Shared by both the player and admin client (an admin is just a `User` row with `IsAdmin=true`).
  - `PlayerService` — the game loop: `listGameTypes`, `joinQueue`, `cancelQueue`, `makeMove`, `sendChatMessage`, `resign`, `rematch`, `getHistory`.
  - `AdminService` — admin actions: `listGameTypes`, `addGameType`, `listUsers`, `listActiveSessions`, `forceEndSession`.

### `server/` — the server process (the only side implemented so far)
- **`server/SessionManager.java`** — in-memory `token → userId` map. `AuthServiceImpl` issues tokens here on login; every other authenticated method resolves the caller's identity through it. Constructor-injected into every `*ServiceImpl` rather than a static/global map, so it's independently unit-testable.
- **`server/ServerMain.java`** — the real entry point. Wires one `SessionManager` into all three service implementations, starts an RMI registry, binds all three under their interface names.
- **`server/rmi/`** — the actual implementations of the three `common/rmi` interfaces:
  - `AuthServiceImpl` — genuinely working (not stubbed), backed by real DAO calls: `register()`/`login()` go through `UserDao` against MySQL, with `jbcrypt` hashing the password (never stored or compared in plaintext). The hardcoded test user from the RMI-skeleton milestone is gone. Real success *and* failure paths, since proving RMI's exception-crossing behavior mattered as much as proving a successful call.
  - `PlayerServiceImpl` — mostly real now: `listGameTypes()`, `getHistory()`, `joinQueue()`, `cancelQueue()`, and `makeMove()` are all genuine (the first two DAO-backed via `GameTypeDao`/`GameSessionDao`; `joinQueue`/`cancelQueue` delegate to `MatchmakingQueue` and `joinQueue` also publishes a `MATCH_FOUND` event via `GameEventPublisher` when it pairs immediately; `makeMove` delegates to `GameEngine` + `GameSessionDao.recordMove()`). Only `sendChatMessage`, `resign`, `rematch` remain deliberate stubs — each throws `UnsupportedOperationException` naming the future roadmap step that will implement it for real.
  - `AdminServiceImpl` — genuinely real now (Milestone 8): a `requireAdmin(sessionToken)` helper (resolve the token, look up the user via `UserDao.findById()`, check `.admin()`, else `NotAdminException`) guards all five methods — `listGameTypes`/`listUsers`/`listActiveSessions` are direct DAO reads, `addGameType` delegates to `GameTypeDao.insert()`, `forceEndSession` delegates to `GameSessionDao.forceEnd()` and, if that actually ended something, publishes `SESSION_FORCE_ENDED` to the session's JMS topic so the two players' clients (not just the admin's own Live Session Monitor) learn the game ended.
- **`server/dao/`** — the JDBC/DAO layer: `UserDao`/`GameTypeDao`/`GameSessionDao` interfaces with `Jdbc*` implementations, a `DataSourceFactory` that lazily builds a shared HikariCP connection pool (so Docker-free tests never trigger a connection attempt), `DaoException` (an unchecked wrapper around `SQLException` for anything that isn't a handled case like a duplicate key), and `ConcurrentGameUpdateException` (unchecked, thrown by `GameSessionDao.recordMove()` when its optimistic-concurrency guard finds the session no longer matches the state the caller validated against — a real expected-race outcome, not a DB failure). `GameSessionDao` also has `findActiveById()`/`findAllActive()`/`forceEnd()` alongside the original `findFinishedSessionsForUser()` (the last two added for Milestone 8's admin client — `forceEnd()` mirrors `recordMove()`'s guarded-UPDATE pattern). `UserDao` also has `findById()`/`findAll()`, and `GameTypeDao` also has `insert()` — both added for the same milestone. Talks to the MySQL schema in `db/schema.sql` via plain JDBC — no ORM.
- **`server/matchmaking/`** — following the same interface + `Jdbc*` implementation pattern as `server/dao/`: `MatchmakingQueue` (interface) / `JdbcMatchmakingQueue` — pairs a caller with the longest-waiting opponent of the same game type and creates the `GameSession` row, all inside a single JDBC transaction, with `join()`/`cancel()` both `synchronized` on the instance so pairing is also protected by a JVM-level lock on top of that transaction. A test-only fake, `InMemoryMatchmakingQueue` (in `src/test/java/...`), lets `PlayerServiceImplTest` exercise `joinQueue`/`cancelQueue` without Docker, mirroring how `server/dao/` has `InMemory*Dao` fakes for the same reason. **Note:** `JdbcMatchmakingQueue.join()` still doesn't set `GameSession.BoardState` when creating a match — `PlayerServiceImpl.makeMove()` compensates by falling back to `GameEngine.initialState()` when it reads a `null` board, rather than matchmaking initializing it. That division of responsibility was a deliberate call in the game-engine design doc, not an oversight — see Milestone 6 in `build-plan.md`.
- **`server/jms/`** — the async server→client push layer, following the same interface + real-impl (+ test-fake where useful) pattern: `GameEventPublisher` (interface) / `ActiveMqGameEventPublisher` — publishes a `GameEventDTO` as a JMS `ObjectMessage` over one of two destination shapes: `publishToPlayer(int userId, GameEventDTO event)` sends to a per-player `Queue` named `player.{userId}.events` (exactly one consumer, used for the pre-session `MATCH_FOUND` case where no session exists yet); `publishToSession(int sessionId, GameEventDTO event)` sends to a per-session `Topic` named `session.{sessionId}.events` (pub/sub — every subscriber gets every message, used for `MOVE_MADE` and `SESSION_FORCE_ENDED` so both players *and* an admin's Live Session Monitor can all observe the same event without stealing it from each other). **The two destination types have different delivery guarantees, and any consumer needs to know this:** a Queue message waits on the broker until *some* consumer eventually receives it, even if none was attached yet at send time — so subscribing to a player queue can safely happen *after* an RMI call that might have already triggered the event, with no lost-message window. A Topic gives no such retention to a non-durable subscriber — a message published before you subscribe is gone for good — so any session-topic consumer (`client.logic.GameClientService`, `admin.logic.AdminClientService`) must subscribe the instant it learns a session id exists, before anything else, or it can silently miss an early event. `JmsConnectionFactory.createForBroker(String brokerUrl)` builds a connection against any broker URL; `create()` (used only by tests) calls it with a disposable, uniquely-named, in-process `vm://matchmaker-<uuid>` broker, fully isolated per call. `ServerMain` itself uses `EmbeddedJmsBroker.start(port)` instead, which starts one long-lived embedded broker with a real `tcp://` transport connector (port `ServerMain.JMS_PORT`, 61616) — still no Docker or separate broker process, but now reachable from a genuinely separate client process over the network, which the disposable `vm://` broker never could be (see Milestone 7 in `build-plan.md` for why this changed — the player client needs to subscribe from its own JVM). `JmsPublishException` (unchecked) wraps a `JMSException` from a failed publish; callers (`PlayerServiceImpl.joinQueue()` for `MATCH_FOUND`, `PlayerServiceImpl.makeMove()` for `MOVE_MADE`, `AdminServiceImpl.forceEndSession()` for `SESSION_FORCE_ENDED`) catch it and log rather than fail the caller's own already-successful result. Test-only fakes live in `src/test/java/.../jms/`: `InMemoryGameEventPublisher` (records what was published to each destination, for assertions) and `FailingGameEventPublisher` (always throws both methods, for proving a publish failure doesn't break the caller). `GameEventType` (`common/enums/`) has three values today: `MATCH_FOUND`, `MOVE_MADE`, and `SESSION_FORCE_ENDED` — no separate `GAME_ENDED` type for the normal win-via-move case, since `MOVE_MADE`'s `GameStateDTO` payload already carries `status`/`winnerId` and a subscriber just inspects those; `SESSION_FORCE_ENDED` earns its own type precisely because *no move happened*, so reusing `MOVE_MADE` for it would be a lie. Chat/resign broadcasts aren't wired to any event yet — those roadmap steps (`sendChatMessage`, `resign`) are still `UnsupportedOperationException` stubs in `PlayerServiceImpl`.
- **`server/game/`** — the rules-engine layer, split into a generic contract and a game-specific implementation package so a future non-board game type doesn't have to fight this one's assumptions:
  - `server/game/` itself holds only what's genuinely game-agnostic: `GameEngine` (interface — `initialState()`, `isLegalMove(String stateJson, boolean isPlayer1Turn, String movePayloadJson)`, `applyMove(...)`, `checkWinner(String stateJson, boolean isPlayer1ToMoveNext)`; both state and a move are opaque JSON strings at this layer, nothing checkers-specific) and `GameResult` (`CONTINUE`/`PLAYER1_WINS`/`PLAYER2_WINS`/`DRAW`, shared because the whole system — `GameSession.Player1ID`/`Player2ID`, matchmaking, rematch, JMS topics — is spec-mandated exactly-2-player; that assumption was deliberately left alone, only the move/state *shape* was generalized).
  - `server/game/checkers/` holds everything checkers-specific, coupled to nothing outside itself except implementing `GameEngine`: `CheckersEngine` (the real implementation — full rules: mandatory capture, multi-jump chains that must continue while a further jump exists, king promotion that ends a chain immediately even if the new king could jump again, no "majority capture" rule, no draw detection), `CheckersBoard` (package-private grid helper — sparse-JSON board serialization, `{"rows":8,"cols":8,"pieces":{"b6":"b",...}}`), `Move`/`Square` (checkers' own move-path and algebraic-square types, parsed/serialized entirely inside `CheckersEngine` — never exposed through `GameEngine`'s signature). A future `server/game/cards/` (or similar) would follow the identical pattern with its own move/state JSON shape.
  - No test-fake exists for `GameEngine` — `CheckersEngine` has no I/O or external dependency to fake around, so tests use it directly (`src/test/java/.../game/checkers/CheckersEngineTest.java` etc.).

### `client/` — the JavaFX player client (the second process, separate from `server/`)
Three packages, per spec §4's mandated Presentation/Logic/Communication split — each only ever calls the layer directly below it:

- **`client/communication/`** — `ServerConnection` (interface: every `AuthService`/`PlayerService` RMI call, plus `subscribeToPlayerQueue`/`subscribeToSessionTopic` returning a closeable `Subscription`; no `RemoteException` in any signature, wrapped instead as the unchecked `ServerCommunicationException`) / `RmiJmsServerConnection` (real impl — RMI stub lookups via `LocateRegistry.getRegistry`, a JMS `Connection` to the server's `tcp://` broker) / `ServerEventListener` (functional interface for a pushed `GameEventDTO`). Test-only fake in `src/test/java/.../client/communication/`: `InMemoryServerConnection` (configurable results/failures, records calls, lets a test manually fire a queued/topic event to simulate a server push — same role as `InMemoryGameEventPublisher` on the server side). Deliberately does not import anything from `com.matchmaker.server.*` — client and server are meant to be independently deployable, even though this course project keeps them in one Maven module; a few lines (JMS connection setup, port numbers) are duplicated rather than shared across that boundary.
- **`client/logic/`** — `GameClientService`, the whole Logic layer for this milestone (one class, not one per screen — revisit only if it grows unwieldy). Wraps every `ServerConnection` call on a background thread and delivers results via `Platform.runLater`, so `client/presentation/` never touches a raw thread. Owns the client-side session state (current `UserDTO`/session token) and the JMS subscription lifecycle: subscribes to a session's topic the instant a session id is known (before returning control to any caller — see the Queue-vs-Topic delivery-guarantee note on `server/jms/` above), and reuses the exact `onMatched` callback passed into `joinQueue()` for both the immediate-match and the deferred-`MATCH_FOUND`-push cases. Fully unit-tested (`GameClientServiceTest`, 11 tests) against `InMemoryServerConnection` — no RMI/JMS/JavaFX runtime involved beyond `Platform.startup()` itself.
- **`client/presentation/`** — FXML + Controller per screen, `SceneNavigator` (swaps the primary `Stage`'s root between loaded FXML files), and `ClientMain` (the `javafx.application.Application` entry point, run via `mvn javafx:run`): `LoginView.fxml`/`LoginController` (login and register share one screen), `LobbyView.fxml`/`LobbyController` (lists game types, Join Queue), `MatchmakingWaitView.fxml`/`MatchmakingWaitController` (has no `onMatched`-style method of its own — `GameClientService` already stores and reuses the original callback, so the deferred match navigates to the Game Board directly regardless of which screen happens to be showing), `GameBoardView.fxml`/`GameBoardController` (renders `BoardState` as an 8×8 grid, only dark squares clickable per `(row+col)%2==1`; builds a move by clicking an origin square then each destination square in order, producing the same `{"path":[...]}` shape `Move.fromJson()` already parses — covers both single steps and mandatory multi-jump chains with one interaction model). No automated tests for this package — consistent with how JavaFX UI isn't unit-tested elsewhere in this stack.

### `admin/` — the JavaFX admin client (a third, separate process, independent of `client/` and `server/`)
Same three-package split as `client/`, per spec §4:

- **`admin/communication/`** — `AdminConnection` (interface: every `AdminService` RMI call plus `subscribeToSessionTopic`, read-only — admin never publishes) / `RmiJmsAdminConnection` (real impl) / `ServerEventListener` (functional interface for a pushed `GameEventDTO`). Test-only fake in `src/test/java/.../admin/communication/`: `InMemoryAdminConnection`. Deliberately duplicates the small shared-shape pieces (`ServerEventListener`, `Subscription`, the unchecked `AdminCommunicationException`) rather than importing them from `client.communication` — same reasoning as `client` not importing from `server`: a few lines of duplication beats a dependency between two things the spec draws as separate boxes.
- **`admin/logic/`** — `AdminClientService`, the whole Logic layer (one class, simpler than `GameClientService` — no matchmaking-style deferred-callback handoff, since monitoring a session is an explicit per-screen action, not something that starts automatically at login). Same background-thread-plus-`Platform.runLater` contract as `GameClientService`. Fully unit-tested (`AdminClientServiceTest`, 11 tests) against `InMemoryAdminConnection`.
- **`admin/presentation/`** — FXML + Controller per screen, `SceneNavigator` (own copy, same fixed-window-size pattern as `client.presentation`'s), and `AdminMain` (the `javafx.application.Application` entry point, run via `mvn javafx:run -Padmin` — a Maven profile swaps `javafx-maven-plugin`'s `mainClass` since the plugin only supports one per plain invocation): `AdminLoginView.fxml`/`AdminLoginController` (no self-service registration; rejects a successfully-authenticated non-admin account client-side as a UX guard, though the real boundary is server-side `NotAdminException`), `DashboardView.fxml`/`DashboardController` (active-sessions `TableView` + user count, both from real `AdminService` calls — no tiles for data nothing backs), `AddGameTypeView.fxml`/`AddGameTypeController`, `LiveSessionMonitorView.fxml`/`LiveSessionMonitorController` (read-only board — same JSON-rendering approach as `client.presentation.GameBoardController` but duplicated, not shared, with no click handlers since admin never moves; live-updates on both `MOVE_MADE` and `SESSION_FORCE_ENDED` pushes). No automated tests for this package, same reasoning as `client.presentation`.

## `src/test/java/com/matchmaker/` — tests

Mirrors the main tree package-for-package. Six different kinds of test appear, deliberately:

1. **Plain unit tests** (`SessionManagerTest`, `AuthServiceImplTest`, `PlayerServiceImplTest`, `AdminServiceImplTest`, the exception hierarchy test) — call methods directly as ordinary Java objects, no networking at all. Fast, and they isolate business logic from RMI plumbing.
2. **Serialization round-trip tests** (`NewDtoSerializationTest`, `ExistingDtoSerializationTest`) — actually serialize a DTO to bytes and back (`ObjectOutputStream`/`ObjectInputStream`), the same mechanism RMI uses internally. Proves the DTOs are RMI-safe, not just that they compile.
3. **Real RMI integration tests** (`AuthServiceRmiIntegrationTest`, `ServerMainTest`) — start an actual `Registry` on a test-only port, look up a genuine stub via `Registry.lookup()`, and call through it. These are the tests that prove RMI itself works end-to-end, automatically, on every `mvn test` run — no manual two-terminal demo required to trust it. Both stay Docker-free: `AuthServiceRmiIntegrationTest` runs `AuthServiceImpl` against in-memory fake DAOs, and `ServerMainTest` relies on Hikari's lazy pool initialization (`DataSourceFactory` never opens a real connection just from being constructed).
4. **DB-integration tests** (`UserDaoTest`, `GameTypeDaoTest`, `GameSessionDaoTest`, `MatchmakingQueueTest`, `DataSourceFactoryTest`) — run real SQL against a real MySQL, started with `docker compose up -d` (see `docker-compose.yml` / `db/schema.sql`), clearing every table in `@BeforeEach` via a shared `TestDatabase.cleanAll(DataSource)` helper (`src/test/java/com/matchmaker/server/TestDatabase.java`) and inserting whatever fixture rows each test needs. These are the *only* tests in the whole suite that require Docker; everything else in this list stays Docker-free. `GameSessionDaoTest` is the one to look at for a real ELO-transaction example and for the concurrent-`recordMove()`-rejection test. **These run against `matchmaker_test`, a database entirely separate from the real `matchmaker`** (`src/test/resources/db.properties` overrides `DataSourceFactory`'s config purely by being on the test classpath — no code involved), so their per-test table-clearing can never touch dev/demo data sitting in `matchmaker`.
5. **Real JMS integration tests** (`GameEventPublisherJmsIntegrationTest`, `JmsConnectionFactoryTest`) — same idea as the RMI integration tier, but for the async side: a real `MessageConsumer` receives a real published `ObjectMessage` over an actual (embedded, in-process) ActiveMQ broker. Docker-free, since the broker is `vm://`-embedded rather than a separate process.
6. **Pure rules-engine tests** (`server/game/checkers/CheckersEngineTest`, `SquareTest`, `MoveTest`) — no DB, no RMI, no JMS; call `CheckersEngine` directly. `CheckersEngineTest` is the largest single test class in the suite (25 tests) and the one most worth reading before extending the rules engine — every test board is a small, explicit JSON literal built from verified `(row+col)%2` parity math, not the full starting position, specifically so each rule (single step, capture, multi-jump chain, promotion, mandatory capture, win detection) can be tested in isolation. **If you add a new test board position, verify the square colors with actual arithmetic before trusting a hand-picked algebraic name** — this bit twice during Milestone 6 (see `build-plan.md`).

Each completed (or in-progress) milestone has this same pair: a **design doc** (`specs/` — the *why*, decisions and rationale, written and agreed before any code) and an **implementation plan** (`superpowers/plans/` — the *how*, broken into bite-sized, TDD-ordered tasks). The `superpowers/` subfolder name comes from the workflow used to produce those docs (brainstorm → plan → subagent-driven implementation with review); it's just a naming artifact of that process, not a meaningful structural distinction from `specs/` at the top level.

## Quick orientation: "where do I add X?"

| Adding... | Goes in |
|---|---|
| A new field that needs to travel over RMI/JMS | `common/dto/` |
| A new kind of failure a remote call can throw | `common/exceptions/` (extend `MatchmakerException`) |
| A new remote method | The relevant interface in `common/rmi/`, then its implementation in `server/rmi/` |
| Real (non-stub) logic for an existing `PlayerService`/`AdminService` method | `server/rmi/PlayerServiceImpl.java` or `AdminServiceImpl.java` — replace the `UnsupportedOperationException` |
| Database access | `server/dao/` — add a `*Dao` interface + `Jdbc*Dao` implementation, following `UserDao`/`JdbcUserDao` |
| Matchmaking/queue logic | `server/matchmaking/` — `MatchmakingQueue`/`JdbcMatchmakingQueue`, following the same interface + `Jdbc*` implementation pattern as `server/dao/` |
| An async server→client push event | `server/jms/` — `GameEventPublisher`/`ActiveMqGameEventPublisher`; add the new case to `GameEventType` (`common/enums/`) and extend `GameEventDTO` (`common/dto/`) if it needs more than `sessionId`/`gameState` |
| Rules for the existing game (checkers) | `server/game/checkers/` — extend `CheckersEngine`; **do not** put checkers-specific types in `server/game/` itself |
| Rules for a *new* game type (non-checkers) | A new sibling package, e.g. `server/game/cards/`, implementing `GameEngine` (`server/game/`) with its own move/state JSON shape — do not try to reuse `server/game/checkers/`'s `Move`/`Square`/`CheckersBoard` |
| Player-facing UI | `client/presentation/` — a new screen gets an `.fxml` file plus a paired `*Controller.java`; wire it to `GameClientService` (`client/logic/`), never straight to `ServerConnection` |
| Admin-facing UI | `admin/presentation/` — a new screen gets an `.fxml` file plus a paired `*Controller.java`; wire it to `AdminClientService` (`admin/logic/`), never straight to `AdminConnection` |
