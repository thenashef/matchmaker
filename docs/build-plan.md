# MatchMaker – Build Plan

## Context
This is a from-scratch final project for an Advanced Java course (see `../MatchMaker_Spec_EN.md` for the full functional/DB/UI spec). No code exists yet. The goal here is twofold: (1) lay out the full sequence of steps to build the system, and (2) start actual coding with the RMI contract layer, since RMI (together with JMS) is the architectural backbone the whole system — and likely the course grading — depends on. Getting the client/server "contract" right first lets every later piece (DB, JMS, UI) be built against a stable interface instead of guessed at.

## Assumptions (flag if wrong)
- Build tool: **Maven**, single project (not multi-module) — simplest to manage/submit for a course project.
- Java: JDK 21 (installed via Homebrew) + Maven 3.9 — confirmed working (`java -version`, `mvn -v`).
- One Maven project containing multiple runnable `main` classes: `ServerMain`, `ClientMain` (JavaFX), `AdminMain` (JavaFX), rather than splitting into separate Maven modules. Keeps the course submission simple; can be split later if it gets unwieldy.
- MySQL and ActiveMQ are not required to be running yet for the first milestone (RMI only, no DB/JMS wiring yet).

## Working style (important)
This is the user's own course project — they need to understand and agree with every piece of code, not receive a batch of files they didn't review. **One file/concept at a time.** For each piece, explain what it does and why and show the intended content in chat first; the user reviews/pushes back/asks questions; only after agreement does it get written to disk. New work goes through brainstorming (design doc) → writing-plans (implementation plan) → subagent-driven execution with a task review after every task and a final whole-branch review before merge.

## Full Roadmap (in build order)

1. **Project setup** — Maven project, folder/package skeleton, dependencies (JavaFX, MySQL Connector/J, ActiveMQ client), `.gitignore`, git init.
2. **Shared contracts (`common` package)** — DTOs that will travel over RMI and JMS (`UserDTO`, `MoveDTO`, `GameStateDTO`, `ChatMessageDTO`), enums (`GameStatus`, `QueueStatus`), and the RMI remote interfaces (`AuthService`, `PlayerService`, `AdminService`).
3. **RMI server skeleton** — implement the remote interfaces, start an RMI registry, bind the services, and prove connectivity with a real RMI integration test (no real logic yet, just echo/ping-style calls).
4. **JDBC/DAO layer** — create the MySQL schema (6 tables per spec), write `UserDao` first, wire real `register`/`login` behavior into the RMI service.
5. **Matchmaking logic** — `MatchmakingQueue` handling with synchronized/atomic pairing; creates a `GameSession` row when two players match.
6. **JMS setup** — ActiveMQ connection, one topic per game session, server-side producer; a minimal standalone consumer to prove messages arrive before touching the UI.
7. **Game engine** — `GameEngine` interface (`isLegalMove`, `applyMove`, `checkWinner`) with `CheckersEngine` as the first implementation; wire into the RMI `makeMove` call; persist `Move` rows and `BoardState`.
8. **Player client (JavaFX)** — Login/Register → Lobby → Matchmaking wait → Game board, wired to RMI (commands) + JMS (push updates).
9. **Admin client (JavaFX)** — Dashboard, Add Game Type, Live Session Monitor; RMI for actions, read-only JMS subscription for live monitoring.
10. **Edge cases** — `keepAlive`/disconnect handling → `ABANDONED` state, turn timeout, Rematch, per-session authorization checks (only participants + only the player whose turn it is can act).
11. **Testing & polish** — manual multi-client runs, error handling, demo/packaging prep.

## What's Implemented So Far (steps 1–9, merged to `main`)

**What "done" looks like:** a server process is running, exposes bound RMI remote objects, and a separate client can look them up over RMI and successfully call a method on them — proving the client/server wiring works before any real feature is built on top. That's working today.

The design and implementation here ended up superseding the plan originally sketched for this milestone: instead of a single `MatchmakerService.java` interface, the actual contract split into three interfaces (`AuthService`, `PlayerService`, `AdminService`) — see `docs/specs/2026-08-05-contracts-design.md` for that design and `docs/superpowers/plans/2026-08-05-contracts-implementation.md` for how it was implemented. Instead of a throwaway `RmiTestClient.java` `main` method, RMI connectivity is proven by `AuthServiceRmiIntegrationTest` — a real, automated integration test that stands up an RMI registry, binds a real `AuthServiceImpl`, and calls it through a genuine looked-up stub — see `docs/superpowers/specs/2026-08-05-rmi-server-skeleton-design.md` for that design and `docs/superpowers/plans/2026-08-05-rmi-server-skeleton-implementation.md` for how it was implemented.

### Milestone 1 — Contracts (`common` package)
- **Enums:** `GameStatus` (`ACTIVE`/`FINISHED`/`ABANDONED`), `QueueStatus` (`WAITING`/`MATCHED`/`CANCELLED`).
- **DTOs** (all `Serializable`, plain classes — private final fields, one constructor, getters only): `UserDTO`, `MoveDTO`, `GameStateDTO`, `LoginResultDTO`, `GameTypeDTO`, `ChatMessageDTO`.
- **Exceptions** (all checked, all extend `MatchmakerException`): `AuthenticationException`, `UsernameTakenException`, `NotParticipantException`, `NotYourTurnException`, `IllegalMoveException`, `NotAdminException`.
- **RMI interfaces:** `AuthService` (register/login/keepAlive — shared by both client types), `PlayerService` (game-loop calls), `AdminService` (admin actions).
- Full design rationale: `docs/specs/2026-08-05-contracts-design.md`.

### Milestone 2 — RMI server skeleton (`server` package)
- **`SessionManager`** — in-memory `token → userId` map; issues and resolves session tokens.
- **`AuthServiceImpl`** — real (not stubbed) auth logic against one hardcoded test user (`username="test"`, `password="test1234"`) — register/login/keepAlive all have genuine success *and* failure paths.
- **`PlayerServiceImpl` / `AdminServiceImpl`** — structurally complete (implement every interface method, correctly bound in the registry), but every method currently throws `UnsupportedOperationException` naming the future roadmap step that implements it — deliberate stubs, not fakes.
- **`ServerMain`** — starts a real RMI registry on port 1099 and binds all three services.
- **Tests:** unit tests for `SessionManager`/`AuthServiceImpl`/the two stub classes (no networking involved), plus two *real* RMI integration tests — `AuthServiceRmiIntegrationTest` and `ServerMainTest` — that stand up an actual registry, look up genuine stubs, and call through them.
- Full design rationale: `docs/superpowers/specs/2026-08-05-rmi-server-skeleton-design.md`.

### Milestone 3 — JDBC/DAO layer (`server.dao` package)
- **`db/schema.sql` + `docker-compose.yml`** — the real MySQL schema (6 tables per `../MatchMaker_Spec_EN.md`: `User`, `GameType`, `GameSession`, `Move`, `MatchmakingQueue`, `ChatMessage`), plus a `docker compose` service for a local dev MySQL that auto-applies the schema on first boot.
- **`DataSourceFactory`** — builds a HikariCP-pooled `DataSource`; deliberately lazy-init, so constructing it never blocks or fails even without a live database — connections are only attempted when a DAO actually runs a query.
- **`UserDao`/`JdbcUserDao`, `GameTypeDao`/`JdbcGameTypeDao`, `GameSessionDao`/`JdbcGameSessionDao`** — real JDBC DAOs (all in `com.matchmaker.server.dao`) backing users, game types, and game sessions.
- **`AuthServiceImpl.register()`/`.login()`** are now real: DAO-backed, with passwords bcrypt-hashed via jBCrypt — the old hardcoded test user is gone entirely.
- **`PlayerServiceImpl.listGameTypes()` and `.getHistory()`** are now real and DAO-backed — the first two `PlayerServiceImpl` methods to graduate off the `UnsupportedOperationException` stub pattern.
- **`ServerMain`** wired to the real JDBC DAOs via a single shared `DataSourceFactory`-built connection pool.
- **Tests:** a fourth test tier — DB-integration tests (`UserDaoTest`, `GameTypeDaoTest`, `GameSessionDaoTest`) that run real SQL against a real Docker MySQL. `ServerMainTest` and `AuthServiceRmiIntegrationTest` remain Docker-free (in-memory fake DAOs + Hikari's lazy pool init), so the "Docker-free except 3 DAO tests" design goal was achieved.
- Full design rationale: `docs/superpowers/specs/2026-08-07-jdbc-dao-layer-design.md` and `docs/superpowers/plans/2026-08-07-jdbc-dao-layer-implementation.md`.

### Milestone 4 — Matchmaking queue (`server.matchmaking` package)
- **`MatchmakingQueue`** (interface) / **`JdbcMatchmakingQueue`** — pairs a caller with the longest-waiting opponent of the same game type and creates the `GameSession` row, all inside a single JDBC transaction spanning the `MatchmakingQueue` and `GameSession` tables. `join()`/`cancel()` are also `synchronized`, so pairing is protected by one JVM-level lock on top of that transaction — not by DB constraints alone.
- **Atomicity is proven, not just asserted:** `MatchmakingQueueTest` includes a real multi-threaded test — three concurrent `join()` calls fired via `ExecutorService` + `CountDownLatch` — that asserts exactly one pairing happens and exactly one caller is left waiting.
- **`join()` is idempotent** — a user calling it twice before an opponent shows up doesn't create a duplicate `MatchmakingQueue` row (its own dedicated test).
- **`PlayerServiceImpl.joinQueue()` and `.cancelQueue()`** are now real, DAO-backed — the 3rd and 4th `PlayerServiceImpl` methods to graduate off the `UnsupportedOperationException` stub pattern, after `listGameTypes()`/`getHistory()` from Milestone 3.
- **A breaking RMI interface change:** `PlayerService.joinQueue()`'s return type changed from `void` to a nullable `GameStateDTO` — `null` means queued with no opponent yet, non-null means matched immediately. This is necessary because JMS (the async server→client push mechanism) doesn't exist yet, so this return value is currently the *only* way a client learns it was matched instantly; the player who was already waiting has no equivalent notification yet — closing that gap is exactly what step 6 (JMS) is for.
- **`ServerMain`** wired to a real `JdbcMatchmakingQueue` off the same shared `DataSourceFactory` pool.
- **Tests:** `MatchmakingQueueTest` runs real SQL against Docker MySQL (queue-then-wait, opponent-already-waiting, idempotent double-join, cancel, and the 3-way concurrent join). `PlayerServiceImplTest` covers `joinQueue`/`cancelQueue` against an `InMemoryMatchmakingQueue` test fixture, so that tier stays Docker-free.
- Full design rationale: `docs/superpowers/specs/2026-08-08-matchmaking-queue-design.md` and `docs/superpowers/plans/2026-08-08-matchmaking-queue-implementation.md`.

### Milestone 5 — JMS setup (`server.jms` package)
- **`JmsConnectionFactory`** — returns a started `javax.jms.Connection` against an embedded ActiveMQ broker (`vm://matchmaker-<uuid>`, in-process, no Docker/separate broker process). Each call gets a uniquely-named broker so tests stay fully isolated from each other.
- **`GameEventDTO`** (`common.dto`) / **`GameEventType`** (`common.enums`, currently just `MATCH_FOUND`) — the payload published over JMS, same `Serializable` DTO shape as every other DTO.
- **`GameEventPublisher`** (interface) / **`ActiveMqGameEventPublisher`** — publishes a `GameEventDTO` as an `ObjectMessage` to a per-player JMS `Queue` named `player.{userId}.events`. Mirrors the existing DAO/`MatchmakingQueue` interface-plus-real-impl-plus-test-fake pattern (`InMemoryGameEventPublisher` for Docker-free unit tests).
- **`PlayerServiceImpl.joinQueue()`** now publishes a `MATCH_FOUND` event to the opponent the instant a pairing happens — this is the piece that closes the notification gap Milestone 4 deliberately left open (the already-waiting player previously had no way to learn about a match, since their own earlier `joinQueue()` call had already returned `null`). A publish failure is caught and logged (`System.err`), never allowed to fail the calling player's own already-successful `joinQueue()` result.
- **`ServerMain`** wired to a real `ActiveMqGameEventPublisher` off its own JMS session, constructed alongside the existing DB/matchmaking wiring.
- **Tests:** `JmsConnectionFactoryTest` (connection is usable), `GameEventPublisherJmsIntegrationTest` (a real consumer receives a published event end-to-end over the embedded broker — this is the "standalone consumer" proof from the original roadmap step, done as an automated test rather than a manual two-terminal demo), extended `PlayerServiceImplTest` (event published on match, not published when just queuing) and `NewDtoSerializationTest` (round-trip for `GameEventDTO`). All Docker-free.
- Full design rationale: `docs/superpowers/specs/2026-08-09-jms-setup-design.md` and `docs/superpowers/plans/2026-08-10-jms-setup-implementation.md`.

### Milestone 6 — Game engine (`server.game` + `server.game.checkers` packages)
- **`GameEngine`** (interface, `server.game`) — deliberately game-agnostic: `initialState()`, `isLegalMove(String stateJson, boolean isPlayer1Turn, String movePayloadJson)`, `applyMove(...)`, `checkWinner(String stateJson, boolean isPlayer1ToMoveNext)`. Both game state and a move are opaque JSON strings at this layer — nothing checkers-specific (no squares, no paths) appears in the shared contract. `GameResult` (`CONTINUE`/`PLAYER1_WINS`/`PLAYER2_WINS`/`DRAW`, `DRAW` reserved but unproduced) is the only other thing in `server.game` — it's shared because the system is explicitly, spec-mandated 2-player (`GameSession.Player1ID`/`Player2ID`, matchmaking, rematch, and JMS topics all commit to exactly two players — see spec section 1 and table 7.3), so generalizing past that would mean fighting the spec, not just this interface.
- **`server.game.checkers` package** — everything checkers-specific lives here, with zero coupling back to `server.game` beyond implementing `GameEngine`: `CheckersEngine` (the real implementation), `CheckersBoard` (package-private grid helper), `Move`/`Square` (checkers' own move-path and algebraic-coordinate types — parsed from/serialized to JSON *inside* `CheckersEngine`, never exposed through `GameEngine`'s signature). A future non-board game (e.g. a card game) would get its own sibling package (`server.game.cards` or similar) with its own move/state shape and no dependency on anything in `server.game.checkers`.
- **`Square`** converts between algebraic square names (`"b6"`, chess-style file `a`–`h` / rank `1`–`8`) and internal `(row, col)` coordinates — the one place that conversion lives.
- **State and move JSON shapes** (via a new `org.json:json` dependency): game state (`BoardState` in the DB) is a sparse map of only the occupied squares (`{"rows":8,"cols":8,"pieces":{"b6":"b",...}}`); a move (`Move.Payload` in the DB) is a path of algebraic squares (`{"path":["b6","c5"]}` for a step, longer for a multi-jump chain).
- **Full checkers rules in `CheckersEngine`**: diagonal single steps (forward-only for men, either direction for kings), mandatory capture (a non-capturing move is illegal whenever any capture is available for that player), multi-jump chains that must continue while a further jump is available, king promotion at the far rank — with promotion ending a capture chain immediately even if the newly-crowned king could jump again. No "majority capture" rule (a player may choose between two non-overlapping capture options of different lengths) and no draw detection — both deliberately out of scope. Pure logic, no I/O, so no test-fake was needed for this package — tests use `CheckersEngine` directly. `isLegalMove()` parses its own move JSON and returns `false` (not `applyMove()`'s problem) on malformed input; `applyMove()` documents and defensively checks its precondition that the move was already validated (path length, non-empty origin square) rather than failing with a confusing `IndexOutOfBoundsException`.
- **`GameSessionDao`** gains `findActiveById()` and a transactional `recordMove()` — in one transaction: inserts the `Move` row (computing the next `MoveNumber` server-side via `MAX(MoveNumber)+1` rather than trusting a caller-supplied number), updates `GameSession` (`BoardState`, `CurrentTurnUserID`, `TurnStartedAt`, and if the game ended, `Status`/`WinnerID`/`EndTime`) **guarded by `WHERE ID = ? AND CurrentTurnUserID = ? AND Status = 'ACTIVE'`** so a stale/concurrent write can't silently clobber a move that already committed, and if the game ended, updates both players' `Wins`/`Losses`/`Rating` in `User` using standard ELO (K=32) — satisfying the spec's requirement that these update in the same transaction as `WinnerID`/`EndTime`. A guard miss (0 rows updated) throws the new unchecked `ConcurrentGameUpdateException` rather than silently succeeding with stale data.
- **`PlayerServiceImpl.makeMove()`** is now real: resolves the session, checks the caller is a participant (`NotParticipantException`) and it's their turn (`NotYourTurnException`), falls back to `gameEngine.initialState()` when a freshly-matched session's `BoardState` is still `null` (matchmaking never initializes it — see the post-merge review fix below), validates the move against `GameEngine` (`IllegalMoveException` for anything illegal, including a stale/finished/unknown session id), applies it, checks for a winner, and persists everything atomically — catching `ConcurrentGameUpdateException` from `recordMove()` and mapping it to `NotYourTurnException` rather than letting an undeclared `RuntimeException` escape the RMI method.
- **`ServerMain`** wired to a real `CheckersEngine`.
- **Post-merge adversarial review caught two critical, 100%-reproducible bugs, both fixed and covered by regression tests before this milestone was considered done:** (1) every game's *first* `makeMove()` call crashed with an unhandled `NullPointerException`, because `JdbcMatchmakingQueue.join()` (unchanged since Milestone 4) never populates `GameSession.BoardState` — fixed by the `initialState()` fallback above; (2) two concurrent `makeMove()` calls for the same session had no protection against a lost-update race (`recordMove()`'s `UPDATE` had no guard tying it to the pre-move state) — fixed by the `WHERE`-clause guard above. Both were reproduced empirically (a real MySQL deadlock for the second one) before being fixed, not just reasoned about.
- **A follow-up refactor generalized `GameEngine` itself** (see the `server.game`/`server.game.checkers` split above) after a design conversation about supporting a future non-board game type — this happened *after* the initial merge to `main`, as a separate small branch (`generic-game-engine-interface`) merged back in immediately after.
- **Tests:** `SquareTest`/`MoveTest` (coordinate conversion, JSON parsing), `CheckersEngineTest` (25 tests covering every rule above, built from hand-verified board positions — TDD caught several of my own hand-picked example squares being invalid/light squares along the way, all fixed before merge — verify any new board-position test square with actual `(row+col)%2` parity math, not by eye), `GameSessionDaoTest` extended with real-MySQL tests for `findActiveById`/`recordMove` including a real ELO transaction and the concurrent-update rejection, `InMemoryGameSessionDao` extended for Docker-free `PlayerServiceImplTest` coverage of the full `makeMove()` flow (happy path, null-`BoardState` fallback, all three exception paths, unknown-session).
- Full design rationale: `docs/superpowers/specs/2026-08-11-game-engine-design.md` and `docs/superpowers/plans/2026-08-11-game-engine-implementation.md`. (The generic-interface follow-up refactor was a direct in-chat design conversation, not a separate design doc — see the branch's single commit message for the full rationale.)

### Milestone 6.5 — Per-session JMS topic (`server.jms`, `server.rmi` packages)
Closed the notification gap Milestone 6 deliberately left open: `makeMove()` was RMI-only, so the mover got their updated board back synchronously but the opponent had no way to learn a move happened until they polled again.

- **`GameEventPublisher.publishToSession(int sessionId, GameEventDTO event)`** — a second publish method alongside the existing `publishToPlayer`, implemented in `ActiveMqGameEventPublisher` against a JMS **Topic** (`session.{sessionId}.events`) rather than a Queue. The choice matters: a Queue hands a message to exactly one consumer, but a session's move needs to reach *both* players (and later, step 9's admin live-monitor, read-only) — a Topic is pub/sub, so every subscriber gets every message. Proven by a real two-consumer JMS integration test (`GameEventPublisherJmsIntegrationTest.publishToSession_bothSubscribersReceiveTheirOwnCopy`), not just asserted.
- **New event type `MOVE_MADE`** (`GameEventType`) — no separate `GAME_ENDED` type; the `GameStateDTO` payload it carries already has `status`/`winnerId`, so a subscriber just inspects those rather than needing a second event type carrying the same information differently.
- **`PlayerServiceImpl.makeMove()`** now publishes `MOVE_MADE` to the session's topic right after `recordMove()` durably persists the move — unconditionally to both players (not just the non-mover; a Topic doesn't need `joinQueue()`'s per-player asymmetry). A publish failure is caught and logged, never allowed to fail the mover's own already-successful move, mirroring `joinQueue()`'s existing handling.
- **Tests:** two new `GameEventPublisherJmsIntegrationTest` cases (single real consumer receives the event; two simultaneous subscribers both receive their own copy), plus `PlayerServiceImplTest` coverage for the happy-path publish and the publisher-throws case. `InMemoryGameEventPublisher`/`FailingGameEventPublisher` test fakes extended to implement the new interface method.
- No separate design doc — the decisions (Topic vs Queue, one event type, publish-to-both) were worked through in chat and are captured in full in `docs/superpowers/plans/2026-08-13-session-jms-topic-implementation.md`, same as the generic-`GameEngine`-interface refactor.

### Milestone 7 — JavaFX player client (`client` package, roadmap step 8)
Login/Register → Lobby → Matchmaking Wait → Game Board, wired to RMI (commands) + JMS (push updates), built as three layers per spec §4: `client.presentation` (FXML + Controllers), `client.logic` (one `GameClientService` class), `client.communication` (RMI stubs + JMS consumer, zero JavaFX awareness).

- **A prerequisite fix, not part of the client itself:** `server.jms`'s broker was a disposable, uniquely-named, in-process `vm://matchmaker-<uuid>` broker created fresh on every call — invisible outside the JVM that created it, so a separate client process had no way to reach it. `EmbeddedJmsBroker` now starts one long-lived broker with a real `tcp://` connector (`ServerMain.JMS_PORT`, 61616) at server startup; `JmsConnectionFactory` gained `createForBroker(String brokerUrl)` so the disposable per-test `vm://` brokers and the new long-lived `tcp://` one share the same connection-setup code. Proven by `EmbeddedJmsBrokerTest`, which connects two fully independent `Connection`s to the same broker over `tcp://` — simulating a real publisher process and a real separate client process — rather than just asserting the broker starts.
- **`client.communication`** — `ServerConnection` (interface, no `RemoteException` in any signature — wrapped as the new unchecked `ServerCommunicationException`, same reasoning as `server.dao.DaoException` wrapping `SQLException`) / `RmiJmsServerConnection` (real impl) / `InMemoryServerConnection` (test fake), following the same interface + real-impl + test-fake shape as every other swappable component in this codebase.
- **`client.logic.GameClientService`** — the whole Logic layer for this milestone. Every method runs its `ServerConnection` call on a background thread and delivers results via `Platform.runLater`, so `client.presentation` never touches a raw thread. Implements the Queue-vs-Topic delivery-guarantee handling from the design doc: subscribes to a session's JMS Topic the instant a session id is known (before returning control to any caller), and reuses the exact `onMatched` callback passed into `joinQueue()` for both the immediate-match and the deferred-`MATCH_FOUND`-push cases, so there's one navigation-to-game-board path, not two.
- **TDD caught a real bug here, not just style nits:** the first version of `onPlayerQueueEvent` (handling a deferred `MATCH_FOUND` push) called the shared `closePlayerQueueSubscription()` helper to tear down the no-longer-needed queue subscription — but that helper *also* clears `pendingMatchCallback` (correct for the unrelated `cancelQueue()` path, where there's genuinely no callback left to fire), which meant the match notification was silently discarding itself before it could ever reach the waiting player's screen. `GameClientServiceTest.joinQueue_deferredMatchFoundPush_invokesOriginalOnMatchedAndSwitchesSubscriptions` failed deterministically until this was fixed by inlining just the subscription-close, leaving `pendingMatchCallback` alone for the match-firing code a few lines later to consume.
- **`client.presentation`** — four screens (`LoginView`/`LobbyView`/`MatchmakingWaitView`/`GameBoardView`, each FXML + a paired Controller), a `SceneNavigator` swapping the primary `Stage`'s root, and `ClientMain` (the `javafx.application.Application` entry point). `GameBoardController` renders the board from `BoardState` JSON (only dark squares per `(row+col)%2==1`, matching `CheckersBoard`), and builds a move by clicking an origin square then each destination square in order — producing exactly the `{"path":[...]}` shape `Move.fromJson()` already parses, covering both single steps and mandatory multi-jump chains with one interaction model.
- **Tests:** `EmbeddedJmsBrokerTest` (new, cross-process JMS reachability), `GameClientServiceTest` (11 tests, fully Docker/RMI/JMS-free against `InMemoryServerConnection` — login/register success+failure, immediate-match vs queued-and-wait `joinQueue`, the deferred-match-push path, queue/topic subscription lifecycle, `makeMove` success+failure, pushed `MOVE_MADE` reaching the attached update listener). No automated tests for `client.presentation` — consistent with how JavaFX UI isn't unit-tested elsewhere in this stack; verified instead by running the real server plus real client process(es) with `mvn exec:java` / `mvn javafx:run` and confirming a clean startup with no exceptions in the console.
- **Status: code-complete, automated-test-complete, and manually verified in real two-process runs — but not yet played to a finished game.** Confirmed for real (not just automated tests): two separate `mvn javafx:run` processes both logging in, matching via the queue (including the already-waiting player's window transitioning on its own from the `MATCH_FOUND` push, no manual refresh), the board rendering and updating live as moves are exchanged, the "You are playing Black/White" indicator, and the 180°-flipped orientation for White — all confirmed correct via screenshots during manual testing. **Not yet confirmed:** a full game played through to a win/loss screen, and a multi-jump move specifically. See Task 8 in the implementation plan for the remaining checklist items.
- Full design rationale: `docs/specs/2026-08-13-player-client-design.md`. Implementation plan: `docs/superpowers/plans/2026-08-13-player-client-implementation.md`.

**Post-ship fixes found during manual verification** (not part of the milestone's original scope, but landed under it since they were found testing it): a null `BoardState` on a freshly-matched session crashed `GameBoardController.renderBoard()` — `PlayerServiceImpl.joinQueue()` now applies the same `gameEngine.initialState()` fallback `makeMove()` already had, for both its return value and the `MATCH_FOUND` push. An XML comment containing `--` (invalid anywhere in an XML comment, not just at the edges) silently broke `GameBoardView.fxml` entirely. The window resized per-screen instead of staying fixed — `SceneNavigator` now sets one fixed size once. Each player now sees a "You are playing Black/White" indicator, and the board rotates 180° (both rank and file) for whichever player is White, so their own pieces sit at the bottom like Black's already did. Every screen's window title now includes the logged-in username (e.g. `MatchMaker - Game (playera)`), since two side-by-side game windows were otherwise indistinguishable at a glance. **Also:** `mvn test`'s DB-integration tier was repeatedly wiping manually-seeded demo accounts because it shared the real `matchmaker` database — `db/schema.sql` now also creates a fully separate `matchmaker_test` database, and `src/test/resources/db.properties` points tests at it instead (Maven's test classpath ordering makes this override automatic, no code involved). Verified by running the full suite and confirming `matchmaker`'s tables came out byte-for-byte unchanged.

### Milestone 8 — Admin client (`admin` package, roadmap step 9)
Real, DAO-backed `AdminService` (all five methods were `UnsupportedOperationException` stubs since the RMI-skeleton milestone) plus a JavaFX admin client — Dashboard, Add Game Type, Live Session Monitor — built as the same three layers as the player client, fully independent of it.

- **Real server-side work first, not just client UI:** the `IsAdmin` authorization check had never existed anywhere. `AdminServiceImpl` now has a `requireAdmin(sessionToken)` helper (resolve token → `UserDao.findById()` → check `.admin()`, else `NotAdminException`) that all five methods call first. New DAO methods: `UserDao.findById()`/`findAll()`, `GameTypeDao.insert()`, `GameSessionDao.findAllActive()`/`forceEnd()` (the last mirrors `recordMove()`'s guarded-UPDATE pattern — `WHERE ID = ? AND Status = 'ACTIVE'`, so a session that already ended naturally in a race just becomes a no-op, not an error).
- **Force-ending a session notifies the players in it, not just the admin.** New `GameEventType.SESSION_FORCE_ENDED`, published to the session's existing JMS topic via the existing `GameEventPublisher.publishToSession()` — no new publisher method needed. This required one small change to the already-shipped player client: `GameClientService.onSessionTopicEvent()` was hard-filtered to only `MOVE_MADE`; it now also accepts `SESSION_FORCE_ENDED` and routes it through the same board-refresh path.
- **`admin.communication`/`admin.logic`/`admin.presentation`** — the identical three-layer shape as `client.*`, with its own independent `AdminConnection`/`RmiJmsAdminConnection`/`InMemoryAdminConnection` (no shared code with `client.communication`, same reasoning as keeping `client` independent of `server`). One `AdminClientService` (simpler than `GameClientService` — no matchmaking-style deferred-callback handoff, since monitoring a session is an explicit per-screen action). ### Now: `keepAlive`/disconnect → `ABANDONED`, and turn timeout
Concrete starting points, confirmed by grepping the code rather than assumed:
- **`keepAlive` exists but does nothing useful yet.** `AuthServiceImpl.keepAlive()` (`src/main/java/com/matchmaker/server/rmi/AuthServiceImpl.java`) just calls `sessionManager.resolve(sessionToken)` — validates the token exists and returns, no timestamp tracking at all. `SessionManager` (`src/main/java/com/matchmaker/server/SessionManager.java`) has no last-seen field on its `token → userId` map. **Neither client ever calls `keepAlive()`** — confirmed via `grep -rn keepAlive src/main/java/com/matchmaker/client/ src/main/java/com/matchmaker/admin/`, zero hits. All three pieces (server-side timestamp tracking, a timeout sweep that transitions a session to `ABANDONED`, and a periodic client-side caller) need building.
- **A real, already-observed motivating case sits in the database right now**: three `GameSession` rows stuck at `Status = 'ACTIVE'` from earlier manual testing, with no player actually connected — see the note under Milestone 8 above. `AdminServiceImpl.forceEndSession()` is the manual escape hatch that already exists for this; this work's job is to make it automatic. Note that `forceEnd()`'s DB update sets `WinnerID = NULL` and never touches `Wins`/`Losses`/`Rating` — an auto-abandon needs a *different* DAO path, since spec §5 says the server "awards the opponent the win," which means a real `WinnerID` plus the same ELO update `recordMove()` already runs on a normal game end.
- **Turn timeout** (spec: *"per `TurnStartedAt`, the server ends the turn automatically"*) — `GameSession.TurnStartedAt` is already a real column, set on every `recordMove()` (see `JdbcGameSessionDao`), just nothing reads it to enforce a limit yet. **Open design question, not yet settled:** does "ends the turn" mean skip to the opponent with no move made, or forfeit the whole game to them (same as a disconnect)? The spec's wording ("ends the turn," not "ends the game") leans toward skip, but this needs a real decision in the design doc, not an assumption.
- Both need a new background mechanism — nothing on the server runs periodically today. A shared `ScheduledExecutorService`-driven sweep (checking both "has any participant gone silent past the disconnect timeout" and "has the current turn run past the turn-time limit") is the natural place for both checks, since they're the same kind of "server periodically inspects live sessions" work.

### Deferred: Rematch
`PlayerService.rematch(sessionToken, finishedSessionId)` is still a hard `UnsupportedOperationException` stub in `PlayerServiceImpl` — spec: *"A Rematch button creates a new session with the same two players, with the turn order swapped."* Fully self-contained, shares no infrastructure with the two items above — can be picked up independently whenever.

### Deferred: JMS broker-level authentication/authorization
**Found during the per-session-authorization audit (2026-08-14), not originally scoped in the roadmap line, but a real gap directly relevant to spec §5's "before accepting a move, or registering and sending to a session's topic, the server verifies that the player is indeed a participant."** The move-side check is solid (`NotParticipantException`/`NotYourTurnException` in `PlayerServiceImpl.makeMove()`), but the topic-subscription side has no check at all: `EmbeddedJmsBroker`/`JmsConnectionFactory` configure zero authentication on the ActiveMQ broker itself (`broker.addConnector("tcp://0.0.0.0:" + port)` with no security plugin; `factory.createConnection()` with no credentials). Anyone who can open a TCP connection to the JMS port — not even someone logged into MatchMaker — can subscribe to any `session.{id}.events` topic or `player.{userId}.events` queue by name. This is broker-wide, not scoped to one destination type.

**Decision: this needs a real fix (broker-level auth), not a documented limitation or a client-side-only guard — but it's deferred to be done last within step 10**, after keepAlive/disconnect and turn timeout land, on a separate git worktree. The architecture already worked out in chat, to pick up when this is scheduled:
- **Authentication**: reuse the existing RMI session token as the JMS credential (`createConnection(String.valueOf(userId), sessionToken)`) rather than inventing a second credential system. A custom `BrokerFilter` (ActiveMQ's standard extension point — its own `SimpleAuthenticationPlugin` is built the same way) validates the token via the existing `SessionManager.resolve()` inside `addConnection()`, attaching a `SecurityContext` with the resolved identity. The server's own publisher connection (`ActiveMqGameEventPublisher`) authenticates with a "service" credential — a random UUID `ServerMain` generates once at startup, known to nothing outside the server process.
- **Authorization**: ActiveMQ's real `AuthorizationPlugin` + a custom `AuthorizationMap`, checked live against `GameSessionDao`/`UserDao` (no caching layer, same pattern as every other authz check in this codebase). Write/produce rights: only the "service" identity, on every destination — no client (player or admin) can ever publish. Read rights on `player.{userId}.events`: only that userId. Read rights on `session.{sessionId}.events`: the session's two participants, plus anyone with `IsAdmin` (this also satisfies the spec's "admin subscribes read-only to any active session" requirement, via the same mechanism). Anything that doesn't match those two known destination-name patterns: denied by default.
- **Real, structural consequence for existing code**: `RmiJmsServerConnection`/`RmiJmsAdminConnection` currently open their JMS `Connection` in the constructor, *before* RMI login ever happens — that has to change to open the JMS connection only after `login()` returns a token, since the token is now the credential. `ServerConnection`/`AdminConnection` interfaces and their `InMemory*` test fakes are unaffected (this is purely an internal change to the real implementations).
- **Deliberately out of scope even when this lands**: only checked at JMS-connect time, not continuously — an already-open JMS connection isn't forcibly dropped if its token is later invalidated. Live revocation would be new machinery on top of this; revisit only if it turns out to matter once keepAlive/disconnect handling exists.
- New test tier needed: a dedicated integration test standing up a broker with the security plugin installed (against `InMemory*Dao` fakes, Docker-free) proving the ACL rules for real — non-participant denied, participant allowed, admin allowed on any session, no client-side connection can publish.

**The rest of the per-session authorization audit is otherwise complete and clean** — `PlayerServiceImpl`/`AdminServiceImpl`'s RMI-layer checks (`NotParticipantException`/`NotYourTurnException`/`NotAdminException`) cover every method that touches a session or requires admin rights. The JMS gap above is the only finding.

**After step 10, step 11**: testing/polish (manual multi-client runs, error handling, demo/packaging prep) — the last roadmap item.
